# หน้า Checkout, การชำระเงิน และการแจ้งเตือน

> กลับไปหน้าหลัก: [../CLAUDE.md](../CLAUDE.md) · โครงสร้างตารางที่เกี่ยวข้อง: `Orders`, `OrderItems`, `PaymentInfos`, `NotifyConfigs`, `StorePromotions` ดูที่ [database.md](./database.md) · สิทธิ์สมาชิกที่มีผลต่อยอด checkout ดูที่ [auth-and-membership.md](./auth-and-membership.md)

## ราคาขาย default และโปรโมชั่นทั้งร้าน

- **ราคาขาย default** — เมื่อแอดมินกรอกราคาต้นทุน (`Product.CostPrice`) ระบบคำนวณราคาขายเริ่มต้นให้อัตโนมัติจาก `Tenant.DefaultMarkupPercent` (ค่าเริ่มต้นระบบ = 30%) แล้วเติมลงช่องราคาขายให้ แอดมินแก้ไขตัวเลขนี้เป็นราคาอื่นก่อนบันทึกได้เสมอ — เป็นแค่การช่วยกรอกเร็วขึ้น ไม่ใช่การล็อกราคา
- หน้าตั้งค่าร้าน (admin) ต้องมีช่องแก้ `DefaultMarkupPercent` ของร้านได้เอง (ไม่ต้องแก้โค้ด) มีผลกับสินค้าที่เพิ่มใหม่หลังจากนั้น ไม่กระทบราคาสินค้าที่ตั้งไว้แล้ว
- **โปรโมชั่นทั้งร้าน (StorePromotion)** — ส่วนลดที่มีผลกับสินค้าทุกชิ้นพร้อมกัน ตั้งได้ 2 รูปแบบ:
  - `recurring_month` — วนซ้ำทุกปีในเดือนที่กำหนด (เช่น เดือนเกิดเจ้าของร้าน ลด 5% ทั้งเดือน)
  - `date_range` — ช่วงวันที่ตายตัว (เช่น แคมเปญปีใหม่)
- หน้า admin ต้องมีจุดจัดการ `StorePromotion` (เพิ่ม/แก้ไข/เปิด-ปิด) ระบบต้องเช็คทุกครั้งที่คำนวณราคา (หน้ารายการสินค้า, หน้ารายละเอียดสินค้า, checkout) ว่าอยู่ในช่วงเวลาที่โปรโมชั่นมีผลหรือไม่ ถ้ามีหลายโปรโมชั่นซ้อนกัน ให้ใช้ตัวที่ลดมากที่สุดตัวเดียว (ไม่ทบกัน)
- ส่วนลดร้าน (`StorePromotion`) กับส่วนลดสมาชิก (`MemberTier`) ใช้ร่วมกันได้ในออร์เดอร์เดียว โดยหักส่วนลดร้านจาก Subtotal ก่อน แล้วค่อยหักส่วนลดสมาชิกจากยอดที่เหลือ (ดูลำดับการคำนวณเต็มในหัวข้อ checkout ด้านล่าง)

## Flow และสิ่งที่ต้องแสดงในหน้า Checkout

ลำดับขั้นในหน้าเดียว (หรือแยกเป็น step ก็ได้ ขึ้นกับ UX ที่เลือก):

1. **ฟอร์มข้อมูลจัดส่ง** — ชื่อ-นามสกุล, เบอร์โทร, ที่อยู่, ตำบล/แขวง, อำเภอ/เขต, จังหวัด, รหัสไปรษณีย์, หมายเหตุ (ถ้ามี)
   - ถ้าลูกค้าล็อกอินเป็นสมาชิก ให้ดึง `UserAddress` ที่ตั้งเป็น default มา pre-fill ฟอร์มอัตโนมัติ (แก้ไขได้ก่อนกดยืนยัน)
   - คำนวณยอดตามลำดับ: **Subtotal** → เช็คว่ามี `StorePromotion` ที่ `isActive = true` และอยู่ในช่วงเวลาที่กำหนดหรือไม่ (ถ้ามีหลายรายการ ใช้ตัวที่ลดมากที่สุดตัวเดียว ไม่ทบกัน) หักเป็น **ส่วนลดร้าน** → ถ้าลูกค้าล็อกอินเป็นสมาชิก หักส่วนลดเพิ่มจาก `MemberTier` ปัจจุบันต่อจากยอดหลังหักส่วนลดร้าน เป็น **ส่วนลดสมาชิก** → คำนวณค่าจัดส่ง (ฟรีถ้าเข้าเงื่อนไข `MemberTier.freeShippingEnabled`) → **ยอดรวมสุทธิ** — แสดงทุกบรรทัดแยกกันให้ลูกค้าเห็นชัด (Subtotal, ส่วนลดร้าน, ส่วนลดสมาชิก, ค่าส่ง, ยอดรวม)
2. **ส่วนแสดงข้อมูลการโอนเงิน** — ดึงจาก `PaymentInfo` ของ tenant นั้น แสดง:
   - ชื่อธนาคาร, ชื่อบัญชี, เลขที่บัญชี (มีปุ่มกดคัดลอกเลขบัญชี)
   - QR code สำหรับสแกนจ่าย — ถ้ามี `promptpayId` ให้ generate QR แบบไดนามิกตามยอดที่ต้องชำระ (เช่นด้วยไลบรารี `promptpay-qr` + `qrcode`), ถ้าไม่มีให้ fallback ไปแสดง `qrImageUrl` ที่อัปโหลดไว้แทน
   - **กรณีมีระบบผู้ขายหลายราย (marketplace, ดู [marketplace-vendors.md](./marketplace-vendors.md))**: ลูกค้าเห็น**บัญชีเดียว** คือบัญชีของร้าน (`PaymentInfo` ผูกกับ tenant ไม่ใช่ผูกกับ vendor) เสมอ ไม่ว่าตะกร้าจะมีสินค้าของ vendor กี่รายปนกัน — ลูกค้าโอนเงินเข้าบัญชีร้านก้อนเดียว **ไม่ได้โอนตรงให้ vendor** จากนั้นแอดมินร้านค่อยไปโอนเงินส่วนของแต่ละ vendor ต่อเองภายหลังแบบ manual นอกระบบ (อ้างอิงจาก `Vendor.bankName/accountName/accountNumber` ที่บันทึกไว้) — ไม่มีการคำนวณค่าคอมมิชชั่นหรือแบ่ง/ตัดยอดอัตโนมัติในระบบ
3. **ช่องแนบสลิปการโอนเงิน** — อัปโหลดรูป/ไฟล์ slip (บังคับกรอกก่อนกดยืนยันสั่งซื้อ), จำกัดชนิดไฟล์เป็นรูปภาพ/PDF และจำกัดขนาดไฟล์
4. **ปุ่มยืนยันคำสั่งซื้อ** — validate ฟอร์มครบ + มี slip แนบแล้วค่อย submit สร้าง `Order` สถานะเริ่มต้น `pending_verify`

## หลังส่งฟอร์มสำเร็จ — ระบบแจ้งเตือน

เมื่อสร้าง `Order` สำเร็จ ให้อ่านค่าจาก `NotifyConfig` ของ tenant นั้น แล้วส่งแจ้งเตือนไปยังช่องทางที่เปิดใช้งานไว้ (เปิดได้มากกว่า 1 ช่องทางพร้อมกัน):

- **Telegram** — ยิง request ไปที่ Telegram Bot API (`sendMessage` และ `sendPhoto` สำหรับแนบรูป slip) โดยใช้ `botToken` และ `chatId` ที่ตั้งค่าไว้ ข้อความควรสรุป: เลขออร์เดอร์, รายการสินค้า, ยอดเงิน, ข้อมูลผู้สั่งซื้อและที่อยู่จัดส่ง
- **Email** — ส่งอีเมลไปที่ `toAddress` ที่ตั้งค่าไว้ (ผ่านผู้ให้บริการ เช่น Resend/SendGrid) เนื้อหาเดียวกับข้างต้น พร้อมแนบ/ลิงก์รูป slip
- การส่งแจ้งเตือนควรทำแบบ async/background job ไม่ block การตอบกลับลูกค้า และควร log ผลลัพธ์การส่งไว้เผื่อ debug (สำเร็จ/ล้มเหลว)
- หน้า admin ของร้านต้องมีจุดให้ทดสอบส่งข้อความแจ้งเตือน (ปุ่ม "ทดสอบส่ง") เพื่อเช็คว่า `botToken`/`chatId`/`toAddress` ที่กรอกไว้ถูกต้อง

**แจ้งเตือน vendor แยกต่างหาก (เสร็จแล้ว 2026-08-16)** — คู่กับแจ้งเตือนแอดมินด้านบน ไม่ใช่สิ่งเดียวกัน: หลังสร้าง `Order` สำเร็จ ระบบวนดูทุก `vendorId` ที่แตกต่างกันในออร์เดอร์นั้น (จาก `OrderItems.VendorId`, ข้ามถ้าเป็น `NULL` คือสินค้าของร้านเอง) แล้วเรียก `notifyVendorNewOrder()` (`src/lib/notifications/notifyOrder.ts`) ต่อ vendor แต่ละราย แบบ fire-and-forget เหมือนกัน ไม่ block response ลูกค้า:
- **ใช้ bot token ร่วมจาก `NotifyConfig` ของ tenant เดิม** (ไม่ต้องให้แต่ละ vendor มี bot ของตัวเอง) แต่ส่งไปที่ `Vendors.TelegramChatId` ของ vendor รายนั้นแทน chat id ของแอดมิน — ส่งได้ก็ต่อเมื่อ `Vendors.NotifyTelegramEnabled = true` และมี `TelegramChatId` ตั้งไว้ (กรอกให้ที่ `/admin/vendors/[id]/edit`)
- **อีเมลใช้ `Users.Email` เดิมของ user ที่ผูก vendor นั้นอยู่แล้ว** ไม่ต้องกรอกอีเมลแยก — ส่งได้ต่อเมื่อ `Vendors.NotifyEmailEnabled = true` (ยังเป็น stub log เหมือนฝั่งแอดมิน เพราะยังไม่ได้ต่อผู้ให้บริการอีเมลจริง)
- ข้อความสั้นกว่าที่ส่งให้แอดมิน (ไม่มีสรุปเต็ม) — แค่ "📦 มีออร์เดอร์ใหม่ #{orderNumber} เข้าไปดูรายการที่ต้องจัดส่งได้ที่ /vendor/orders" ให้ vendor เข้ามาดูรายละเอียดในระบบเอง
- ทดสอบจริงแล้ว (2026-08-16): สร้างออร์เดอร์ที่มีสินค้าของ vendor → เห็น log `[notify] Telegram แจ้งเตือน vendor #{vendorId} ล้มเหลว...: Unauthorized` (คาดไว้ เพราะ bot token ที่ตั้งไว้ตอน dev เป็น token ปลอม — เหมือนที่แจ้งเตือนแอดมินก็ error แบบเดียวกัน) และ log `[email:stub]` ที่มีเนื้อหาสั้นๆ ตามที่ตั้งใจถูกต้อง — ยืนยันว่า error handling ไม่ทำให้สร้างออร์เดอร์ล้มเหลว (order confirmation แสดงผลปกติ)

## ตรวจสอบสลิปอัตโนมัติ

ใช้ OCR/บริการตรวจสลิป (เช่น SlipOK หรือ API ของธนาคาร) อ่านยอดเงิน/เวลาโอนจากรูป slip แล้วเทียบกับยอดออร์เดอร์อัตโนมัติ ลดภาระแอดมินตรวจเอง โดยยังต้องมีปุ่ม "ยืนยันด้วยมือ" สำรองไว้ในหน้า admin เผื่อระบบอ่านผิดพลาด ผลตรวจ (ตรงกัน/ไม่ตรงกัน/อ่านไม่ได้) ให้บันทึกไว้กับ `Order` เพื่อให้แอดมินเห็นสถานะ

## หน้าติดตามสถานะออร์เดอร์

ลูกค้ากรอกเลขออร์เดอร์ + เบอร์โทรเพื่อดูสถานะ (รอตรวจสอบ/ยืนยันแล้ว/จัดส่งแล้ว) โดยไม่ต้องล็อกอิน ลดคำถามซ้ำเรื่องสถานะพระที่สั่ง

## รองรับ payment gateway

เชื่อมต่อผู้ให้บริการ เช่น Omise, 2C2P หรือ PromptPay ผ่านธนาคารโดยตรง เป็นทางเลือกเสริมควบคู่กับ flow โอน+แนบสลิป เพื่อให้ยืนยันเงินอัตโนมัติแบบเรียลไทม์สำหรับร้านที่ต้องการ ส่วนร้านที่ไม่อยากเสียค่าธรรมเนียม gateway ยังใช้วิธีโอน+แนบสลิปได้ตามปกติ
