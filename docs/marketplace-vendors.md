# ระบบผู้ขายหลายราย (Marketplace ภายในร้านเดียว)

> กลับไปหน้าหลัก: [../CLAUDE.md](../CLAUDE.md) · โครงสร้างตารางที่เกี่ยวข้อง: `Vendors`, `Products.VendorId`, `Users.VendorId`, `OrderItems.VendorId` ดูที่ [database.md](./database.md)

Roadmap ข้อ 8 — เลือก implement เป็น **"หลายผู้ขายในร้านเดียว"** (คล้าย Shopee/Lazada ที่มีร้านค้าย่อยหลายร้านในแพลตฟอร์มเดียว) ไม่ใช่การขยายระบบ multi-tenant เดิม (แต่ละ tenant ยังคือร้าน/โดเมนแยกกันเหมือนเดิมตาม [theming.md](./theming.md)) — vendor คือผู้ขายรายย่อยที่อยู่**ภายใน** tenant เดียว มีสิทธิ์จัดการเฉพาะสินค้า/ดูออร์เดอร์ของตัวเอง

## บทบาทที่เพิ่มเข้ามา

- **Vendor (ผู้ขาย)** — role ใหม่ใน `Users.Role` (`super_admin | tenant_admin | member | vendor`) ผูกกับ `Users.VendorId` → `Vendors` หนึ่งแถว จัดการได้เฉพาะสินค้าของ vendor ตัวเอง (`Products.VendorId`) และดูออร์เดอร์ที่มีสินค้าของตัวเองอยู่เท่านั้น (อ่านอย่างเดียว ไม่แก้สถานะออร์เดอร์)
- `Products.VendorId` เป็น `NULL ได้` — `NULL` = สินค้าของร้านเอง (house product, จัดการผ่าน seed เหมือนเดิมตามที่ CLAUDE.md บันทึกไว้ว่ายังไม่มีหน้า admin จัดการสินค้าของร้านเอง), ไม่ใช่ `NULL` = สินค้าของ vendor รายนั้น
- `Vendors.Status` = `active | suspended` — แอดมิน tenant กดระงับ vendor ได้จาก `/admin/vendors` โดยไม่ต้องลบข้อมูล สินค้าของ vendor ที่ถูกระงับจะถูกซ่อนจากหน้าร้านทันที (ดูหัวข้อ "การมองเห็นสินค้า" ด้านล่าง) แต่ข้อมูลออร์เดอร์เก่ายังอยู่ครบ

## การจัดการผู้ขาย (แอดมิน)

- `/admin/vendors` (เฉพาะ role `tenant_admin`): เพิ่มผู้ขายใหม่ (กรอกชื่อร้าน, ผู้ติดต่อ, เบอร์โทร, อีเมล+รหัสผ่านเริ่มต้นสำหรับให้ vendor ล็อกอิน, ข้อมูลบัญชีธนาคารไว้อ้างอิงตอนโอนเงินให้ vendor), แก้ไขข้อมูลร้าน/บัญชี, ปุ่มระงับ/เปิดใช้งาน
- สร้าง vendor ใหม่ = สร้าง `Vendor` row + `User` row (role `vendor`) พร้อมกันในทรานแซกชันเดียว — แอดมินเป็นคนตั้งรหัสผ่านเริ่มต้นให้ vendor เอง (ไม่มี flow สมัครสมาชิกสาธารณะสำหรับ vendor ในเฟสนี้ เพื่อกันสแปม/ผู้ขายปลอมเข้าระบบเอง) แล้วแจ้งรหัสผ่านให้ vendor นอกระบบ (เช่น โทร/แชท) — vendor เปลี่ยนรหัสผ่านเองยังไม่มี ทำเพิ่มได้ภายหลังถ้าต้องการ
- ไม่มีปุ่มลบ vendor ถาวร (กันข้อมูลออร์เดอร์เก่าอ้างอิงไม่ได้) ใช้ระงับแทน

## การจัดการสินค้า (ผู้ขาย)

- `/vendor` แดชบอร์ดผู้ขาย (ต้องล็อกอินด้วย role `vendor` — คุมเส้นทางผ่าน `src/proxy.ts` matcher `/vendor/:path*`), แสดงจำนวนสินค้า/รายการที่ถูกสั่งซื้อ และแบนเนอร์เตือนถ้าบัญชีถูกแอดมินระงับ
- `/vendor/products` CRUD สินค้าของตัวเอง (`src/lib/vendor-products/actions.ts`) — ทุก action เช็ค `vendorId` จาก session เทียบกับ `Products.VendorId` เสมอ กัน vendor แก้/ดูสินค้าของ vendor รายอื่น
- ฟอร์มสินค้ารองรับฟิลด์เดียวกับสินค้าปกติ (ชื่อ, รายละเอียด, ราคา, ต้นทุน, สต็อก, จังหวัด/หลวงพ่อ/หมวดหมู่, วัด/ยุคสร้าง, ใบรับประกัน) **ยกเว้นรูปสินค้ารองรับแค่ 1 รูปผ่าน URL** (ไม่มีอัปโหลดไฟล์ตรง/รูปใบรับประกันแยก ต่างจากสินค้าที่ seed ไว้ล่วงหน้าซึ่งมีหลายรูป) — เป็นทางลัดสำหรับ dev ตาม pattern เดียวกับที่อื่นในโปรเจกต์ที่ใช้ placeholder URL ไปก่อน
- ปิดการขาย (`isActive = false`) แทนการลบ — สินค้าที่เคยอยู่ในออร์เดอร์เก่ายังอ้างอิงได้ปกติ (เหมือน pattern เดิมของระบบ)

## การมองเห็นสินค้าบนหน้าร้าน

- ทุก query สินค้าฝั่ง storefront (`src/lib/products/queries.ts`, `home/queries.ts`, `provinces/queries.ts`, `monks/queries.ts`) ใช้ตัวกรองร่วม `visibleVendorFilter` (export จาก `products/queries.ts`): แสดงเฉพาะสินค้าที่ `VendorId IS NULL` (สินค้าของร้านเอง) **หรือ** vendor ของสินค้านั้นยังไม่ถูกระงับ (`Vendor.Status != "suspended"`)
- **สำคัญ:** เพิ่ม query สินค้าฝั่ง storefront ใหม่ทุกครั้งต้อง spread `visibleVendorFilter` เข้า `where` ด้วยเสมอ ไม่งั้นสินค้าของ vendor ที่ถูกระงับจะยังโผล่อยู่
- `ProductCard` และหน้ารายละเอียดสินค้าโชว์ป้าย "ขายโดย {ชื่อร้าน}" เมื่อสินค้ามี vendor (ไม่โชว์ถ้าเป็นสินค้าของร้านเอง)
- **ลูกค้าเห็นสินค้าของทุก vendor ที่ active ปนกันในหน้าร้านเดียวกันหมด** (`/`, `/products`, `/provinces/[slug]`, `/monks/[slug]`) — `visibleVendorFilter` ไม่ได้แยกว่าลูกค้าคนไหนควรเห็นของ vendor ไหน แค่กรอง vendor ที่ถูกระงับออกเท่านั้น ตัวกรองที่มีตอนนี้คือจังหวัด/หลวงพ่อ/หมวดหมู่/ช่วงราคา **ไม่มีตัวกรองเลือกดูเฉพาะ vendor ใดวันหนึ่ง** และ**ไม่มีหน้าร้านย่อยสาธารณะของแต่ละ vendor** (เช่น `/shop/[vendorSlug]`) ให้ลูกค้ากดเข้าไปดูเฉพาะสินค้าของ vendor รายนั้น — ป้าย "ขายโดย" ด้านบนเป็นแค่ข้อมูลบอก ไม่ใช่ลิงก์ไปหน้าอื่น

## Checkout และออร์เดอร์

- **ไม่มีการแยกออร์เดอร์/การจ่ายเงินตาม vendor** — ตะกร้าที่มีสินค้าจากหลาย vendor ปนกับสินค้าของร้านเองยังสร้างเป็น `Order` เดียวเหมือนเดิมทุกประการ ลูกค้าจ่ายเงินเป็นก้อนเดียว ไม่ใช่ split-payment แบบ marketplace เต็มรูป (จุดนี้ไม่เปลี่ยน)
- **การจัดส่งแยกตาม vendor ได้ (แก้ไข 2026-08-14, กลับคำตัดสินใจเดิม)** — เดิมเอกสารนี้เคยระบุว่า "จัดส่งเป็นก้อนเดียว ไม่รองรับ vendor แยกกล่องส่งเอง" แต่พิจารณาใหม่แล้วว่าไม่ตรงกับความเป็นจริง เพราะ vendor แต่ละรายเก็บสต็อกและแพ็คของเอง (ไม่ได้ส่งสต็อกมารวมที่คลังร้านล่วงหน้าแบบ Amazon FBA) การบังคับให้พัสดุออกจากที่เดียวจะต้องเพิ่ม flow ใหม่ทั้งหมด (vendor ส่งของมาที่ร้านก่อน แล้วร้านค่อยแพ็ครวมส่งลูกค้าอีกที) ซึ่งเพิ่มขั้นตอน/ต้นทุนขนส่งโดยไม่จำเป็นและไม่เคยอยู่ในแผนเดิม — เปลี่ยนเป็นให้แต่ละ vendor (และร้านเอง ถ้ามีสินค้าของร้านปนอยู่ด้วย) ส่งพัสดุแยกกันตรงถึงลูกค้า **1 order อาจมีหลาย tracking number** (หนึ่งต่อ vendor ที่มีสินค้าในออร์เดอร์นั้น) — ตรงกับพฤติกรรมจริงของ marketplace รายใหญ่ (Shopee/Lazada ก็แยกพัสดุ/tracking ต่อผู้ขายเหมือนกันเมื่อ order มีสินค้าหลายร้าน) ลูกค้าเห็นทุก tracking number ของ order นั้นพร้อมกันที่ `/track-order` — ดูรายละเอียด schema/flow ที่ [vendor-enhancements-plan.md](./vendor-enhancements-plan.md) ข้อ 5
- `OrderItems.VendorId` snapshot ผู้ขาย ณ เวลาซื้อไว้ (เหมือน `ProductName` ที่ snapshot ชื่อสินค้า) กันกรณีสินค้าย้ายเจ้าของ/vendor ถูกลบทีหลัง ทำให้ประวัติออร์เดอร์เก่ายังถูกต้อง — `createOrderAction` (`src/lib/checkout/actions.ts`) อ่าน `product.vendorId` มาใส่ตอนสร้าง `OrderItem` ทุกครั้ง
- `/vendor/orders` อ่านอย่างเดียว: group `OrderItem` ตาม `orderId` แล้วโชว์เฉพาะรายการสินค้าของ vendor ตัวเองในแต่ละออร์เดอร์ + ยอดรวมเฉพาะส่วนของตัวเอง — vendor **ไม่เห็น**รายการสินค้าของ vendor อื่นหรือของร้านเองในออร์เดอร์เดียวกัน และ**แก้สถานะออร์เดอร์ไม่ได้** (สถานะ/การจัดส่งยังเป็นหน้าที่ tenant_admin ที่ `/admin/orders/[id]` เหมือนเดิม)

## ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว

- **รหัสสินค้า (SKU/product code)** (เสร็จแล้ว 2026-08-16) — vendor กรอกเองตอนเพิ่ม/แก้ไขสินค้าที่ `/vendor/products/new` และ `/vendor/products/[id]/edit` (บังคับกรอกเสมอสำหรับสินค้าที่สร้าง/แก้ไขใหม่ — สินค้าเก่าที่ seed ไว้ยังเป็น `NULL` ได้) ไม่ซ้ำกันภายในร้านเดียวกัน (unique filtered index `UX_Products_Tenant_Sku` ต่อ `TenantId`, ข้ามร้านซ้ำกันได้) เช็คซ้ำทั้งฝั่ง client (`required`) และ server (`src/lib/vendor-products/actions.ts` คืน error "รหัสสินค้านี้มีอยู่แล้วในร้าน" ถ้าซ้ำ) — แสดงผลครบทุกจุดตามที่ผู้ใช้ระบุ: หน้ารายละเอียดสินค้า, ตะกร้า, รายการสินค้าของ vendor (`/vendor/products`), รายละเอียดออร์เดอร์ทั้งฝั่งแอดมิน (`/admin/orders/[id]`) และฝั่ง vendor (`/vendor/orders`) — **ไม่ได้ snapshot ลง `OrderItem`** ต่างจาก `ProductName`/`VendorId` เพราะ SKU ถือเป็น identifier ที่เสถียร ไม่ต้องเก็บ historical snapshot จึง join สดจาก `Product.Sku` ตอน query แทน — ทดสอบ end-to-end จริงแล้วใน browser (2026-08-16): vendor เพิ่มสินค้าพร้อม SKU สำเร็จ, กันรหัสซ้ำในร้านเดียวกันได้ถูกต้อง, แสดงผลถูกต้องทุกจุด, ออร์เดอร์เก่าที่ไม่มี SKU (`NULL`) ยัง render ได้ปกติไม่พัง
- **vendor เปลี่ยนรหัสผ่านเองได้** (เสร็จแล้ว 2026-08-16) — หน้าใหม่ `/vendor/settings` (ลิงก์จาก `/vendor` dashboard) มีฟอร์มกรอกรหัสผ่านเดิม + รหัสผ่านใหม่ + ยืนยันรหัสผ่านใหม่ — action `changeVendorPasswordAction` (`src/lib/auth/actions.ts`) เช็ครหัสผ่านเดิมถูกต้องด้วย `verifyPassword()` ก่อนเสมอ (คืน error "รหัสผ่านเดิมไม่ถูกต้อง" ถ้าไม่ตรง), บังคับรหัสผ่านใหม่อย่างน้อย 8 ตัวอักษรและต้องตรงกับช่องยืนยัน (pattern เดียวกับตอนสมัครสมาชิก) แล้ว hash ด้วย `hashPassword()` ก่อนอัปเดต `Users.PasswordHash` — สำเร็จแล้ว redirect กลับหน้าเดิมพร้อม `?success=1` แสดงข้อความ "เปลี่ยนรหัสผ่านสำเร็จ" — ทดสอบ end-to-end จริงแล้วใน browser (2026-08-16): กรอกรหัสผ่านเดิมผิด → error ถูกต้อง, กรอกรหัสผ่านใหม่ไม่ตรงกับยืนยัน → error ถูกต้อง, เปลี่ยนรหัสผ่านสำเร็จ → logout → login ด้วยรหัสผ่านใหม่ได้จริง ("ลืมรหัสผ่าน" ตอนยังไม่ได้ login ไม่รวมอยู่ในฟีเจอร์นี้ ยังเป็นข้อจำกัดเดิมเหมือน member)

## แผนที่จะเพิ่ม (ยังไม่ได้ทำ): ฟีเจอร์เสริมฝั่ง vendor

ตอนนี้ vendor ไม่รู้เลยว่ามีออร์เดอร์ใหม่เข้ามา ต้องเข้ามาเช็คเองที่ `/vendor/orders` (ดูหัวข้อ "Checkout และออร์เดอร์" ด้านบน) — ผู้ใช้ระบุ requirement เพิ่มไว้ดังนี้ ยังไม่ได้ implement:

1. **เมื่อลูกค้าสั่งซื้อสินค้า ให้แจ้งเตือนไปยัง admin เหมือนเดิมตามที่มีอยู่แล้ว ไม่เปลี่ยนแปลง** — คือ flow `notifyNewOrder()` ที่อ่านค่าจาก `NotifyConfig` (1 ชุดต่อ tenant) แล้วส่ง Telegram/Email ไปหาแอดมินร้านตามที่ตั้งค่าไว้ที่ `/admin/notifications` (ดู [checkout-and-payment.md](./checkout-and-payment.md)) — ส่วนนี้ยังคงเดิม ไม่ต้องแก้
2. **เพิ่มหน้าสำหรับ `tenant_admin`/`super_admin`** เพื่อดู/ส่งสรุปรายการสั่งซื้อไปให้ vendor แต่ละราย โดยสรุปต่อ vendor ให้เห็น:
   - รหัสสินค้าและชื่อสินค้าที่ถูกสั่งซื้อ (แต่ละรายการ)
   - สรุปยอด (จำนวน/ยอดรวม)
   - ที่อยู่จัดส่งของลูกค้าแต่ละราย — **แยกกลุ่มตามที่อยู่ลูกค้า** (ออร์เดอร์เดียวอาจมีสินค้าหลาย vendor ปนกัน ต้องแตกเป็นก้อนแยกตามลูกค้า/ที่อยู่ ให้ vendor เห็นชัดว่าต้องแพ็ค-ส่งอะไรไปที่ไหนบ้าง)
   - มีปุ่ม **"Send Notify"** ให้แอดมินกดส่งแจ้งเตือนไปหา vendor รายนั้น เพื่อบอกให้เข้ามาดูรายการที่ต้องจัดส่งในระบบ (ตัวข้อความแจ้งเตือนไม่จำเป็นต้องมีสรุปเต็มในตัวเอง แค่แจ้งว่ามีออร์เดอร์ใหม่ให้เข้ามาดูที่ `/vendor/orders`) — **เลือก/config ได้ว่าจะส่งผ่าน Telegram, Email หรือทั้งคู่** (checkbox เลือกช่องทางตอนกด หรือ config ไว้ล่วงหน้าต่อ vendor ก็ได้ ทำนองเดียวกับที่ `NotifyConfig` มี `telegramEnabled`/`emailEnabled` แยกกันในระดับ tenant) — ต้องเพิ่มช่องเก็บช่องทางแจ้งเตือนต่อ vendor เอง (เช่น `Vendor.telegramChatId` และใช้อีเมล login ของ `User` ที่ผูกกับ vendor นั้น) เพราะ `NotifyConfig` ปัจจุบันมีแค่ 1 ชุดต่อ tenant ใช้กับ vendor แต่ละรายแยกกันไม่ได้ — ฝั่งอีเมลต้องต่อผู้ให้บริการจริง (เช่น Resend/SendGrid) ก่อนถึงจะส่งได้จริง เพราะตอนนี้ยังเป็นแค่ stub log (ดู [checkout-and-payment.md](./checkout-and-payment.md))
3. **เพิ่มเลขพัสดุ/tracking number** — ปัจจุบัน `Order` มีแค่ `status` enum (`pending_verify | verified | shipped | cancelled`) ไม่มี field เก็บเลขพัสดุเลย ให้ทำตามแนวทางที่ระบบ marketplace ทั่วไปใช้กัน:
   - **แยกเป็นตาราง `Shipment` ต่างหาก** ผูกกับ `(orderId, vendorId)` แทนที่จะแปะ column เดียวใน `Order` เก็บ `carrierName` + `trackingNumber` + `shippedAt` — เหตุผล: ออร์เดอร์เดียวอาจถูก vendor หลายรายแพ็คส่งแยกกัน (คนละเลขพัสดุ) เชื่อมกับข้อจำกัดเดิมเรื่อง "ไม่มี split-shipping ต่อ vendor" ด้านล่าง ถ้าจะรองรับ tracking number ต่อ vendor จริงต้องแก้จุดนี้ควบคู่กันไป
   - **`carrierName` เป็น dropdown รายชื่อขนส่งที่พบบ่อยในไทย** (ไปรษณีย์ไทย, Kerry, Flash, J&T, Ninja Van, DHL ฯลฯ) **+ ช่อง free-text สำรอง** เผื่อขนส่งที่ไม่อยู่ใน list
   - **Auto-generate ลิงก์ติดตามพัสดุ** จาก URL template ต่อขนส่ง (เช่น `https://track.thailandpost.co.th/?trackNumber=XXXX`) แสดงเป็นลิงก์กดได้ตรงในหน้า `/track-order` ให้ลูกค้า
   - **ไม่ต้องต่อ API ขนส่งเพื่อดึงสถานะอัตโนมัติแบบเรียลไทม์** (เช่น "อยู่ระหว่างขนส่ง"/"นำจ่ายแล้ว") — ตัดออกจาก scope นี้ ซับซ้อนเกินความจำเป็นตอนนี้
   - **แจ้งเตือนลูกค้าอัตโนมัติทันทีที่กรอกเลขพัสดุ (SMS/email)** — ให้เพิ่ม field/จุดเชื่อมไว้ในโค้ดตามแผนนี้ได้ แต่ **ปิดการใช้งานไว้ก่อน (ยังไม่เปิดใช้จริงตอนนี้)** เพราะการส่ง SMS/email จริงต้องต่อผู้ให้บริการเพิ่ม (เหมือนข้อจำกัดเดิมเรื่องอีเมลที่ยังเป็น stub)
4. **ระบบจ่ายเงินให้ vendor (payout)** — ตอนนี้เป็น manual ล้วน (แอดมินโอนเองนอกระบบเมื่อไหร่ก็ได้ ดูหัวข้อ "ขอบเขตที่ยังไม่ทำ" ด้านล่าง) ให้ปรับตามแนวทางที่ระบบ marketplace ทั่วไปใช้กัน (ไม่เอาส่วน "จ่ายไว/instant payout" ที่เป็นออปชันเสริม):
   - **Escrow ก่อนปล่อยเงิน** — เงินลูกค้าเข้าบัญชีร้าน (`PaymentInfo` เดิม) ก่อนเสมอ ไม่ปล่อยให้ vendor ทันทีที่ลูกค้าจ่าย ต้องรอจนเข้าเงื่อนไข: ลูกค้ายืนยันรับสินค้าแล้ว หรือพ้นระยะเวลาคืนสินค้าที่กำหนด (เช่น 3-7 วันหลังสถานะเป็น `shipped`) โดยไม่มีการเคลม/ขอคืนเงิน — ต้องมี field ใหม่เก็บสถานะนี้ต่อ `OrderItem`/`Shipment` เช่น `payoutEligibleAt`/`payoutStatus` (pending/eligible/paid)
   - **จ่ายเป็นรอบ (settlement cycle)** ไม่ใช่จ่ายทีละออร์เดอร์ — รวมยอด `OrderItem` ของ vendor ที่ `payoutStatus = eligible` ในแต่ละรอบ (เช่น ทุกสัปดาห์/ทุก 15 วัน ตั้งค่าได้) แล้วให้แอดมินดูสรุปยอดที่ต้องโอนต่อ vendor ต่อรอบ (คล้ายหน้าสรุปส่งให้ vendor ในข้อ 2 แต่เป็นสรุปเงินแทนสรุปสินค้า)
   - **ค่าใช้จ่ายที่ vendor ต้องเสียให้ระบบ ก่อนคำนวณยอดจ่ายสุทธิ** — จำกัดไว้แค่ 2 อย่างที่จำเป็นกับ scope ร้านนี้ (ไม่เอาค่าธรรมเนียมแรกเข้า/รายเดือน, ค่าโฆษณา/บูสสินค้า, ค่าปรับ, ค่าคลังสินค้า ที่เกินความจำเป็นสำหรับร้านขนาดนี้):
     - **ค่าคอมมิชชั่นต่อยอดขาย** — % ของยอดขายต่อชิ้น/ต่อออร์เดอร์ เก็บเป็น field `Vendor.commissionPercent` (ต่อ vendor แต่ละราย จะได้ตั้งอัตราไม่เท่ากันได้ถ้าต้องการ)
     - **ค่าธรรมเนียมการชำระเงิน (payment/gateway fee)** — เกิดเฉพาะออร์เดอร์ที่ลูกค้าจ่ายผ่าน payment gateway จริง (ไม่ใช่โอน+แนบสลิป) หักตามอัตราที่ผู้ให้บริการ gateway เรียกเก็บจริง
     - รวมสองอย่างแล้วคำนวณยอดสุทธิที่ vendor ได้รับจริง = ยอดขาย − ค่าคอมมิชชั่น − ค่าธรรมเนียม gateway (ถ้ามี) ก่อนแสดงในหน้าสรุปยอดจ่ายรายรอบ
   - ยังคง**ไม่มีการโอนเงินอัตโนมัติจริงในระบบ** (ไม่ต่อ bank API/promptpay transfer API) — ระบบแค่คำนวณ/สรุปยอดที่ต้องจ่ายให้ถูกต้องต่อรอบ ส่วนการโอนจริงแอดมินยังกดโอนเองนอกระบบเหมือนเดิม แล้วมาติ๊กว่า "จ่ายแล้ว" ในระบบเพื่ออัปเดต `payoutStatus`

## ขอบเขตที่ยังไม่ทำ (ตัดสินใจจำกัด scope ตอนสร้างฟีเจอร์นี้)

- **ไม่มีค่าคอมมิชชั่น/ระบบตัดยอด/payout อัตโนมัติ** — เก็บแค่ข้อมูลบัญชีธนาคารของ vendor ไว้อ้างอิง (`Vendor.BankName/AccountName/AccountNumber`) ให้แอดมินโอนเงินให้ vendor เองนอกระบบ เหมือนที่ระบบตรวจสลิปลูกค้าก็เป็น manual (ดู [checkout-and-payment.md](./checkout-and-payment.md)) — มีแผนจะทำ (escrow + รอบจ่าย + หักคอมมิชชั่น แต่ไม่มีโอนเงินอัตโนมัติจริง) ดูข้อ 4 ในหัวข้อ "แผนที่จะเพิ่ม" ด้านบน
- **ไม่มี public vendor registration/approval flow** — เฉพาะ tenant_admin สร้างบัญชี vendor ให้เท่านั้น
- ~~ไม่มี split-shipping ต่อ vendor~~ **ยกเลิกข้อจำกัดนี้แล้ว (2026-08-14)** — เปลี่ยนเป็นรองรับ split-shipping ต่อ vendor (1 order อาจมีหลาย tracking number) ดูหัวข้อ "Checkout และออร์เดอร์" ด้านบน และแผนงานที่ [vendor-enhancements-plan.md](./vendor-enhancements-plan.md) ข้อ 5 (ยังไม่ได้ implement — อยู่ระหว่างวางแผน)
- ~~vendor เปลี่ยนรหัสผ่านเองยังไม่มี~~ **ทำแล้ว (2026-08-16)** — ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน ("ลืมรหัสผ่าน" ตอนยังไม่ได้ login ยังไม่รวมอยู่ในนี้ ยังเป็นข้อจำกัดเดิม เหมือนกับ member ที่ยังไม่มีหน้า "ลืมรหัสผ่าน" เช่นกัน)
- **vendor แก้ theme ร้านหรือเลขบัญชีธนาคารรับเงินของตัวเองไม่ได้** — พอร์ทัล `/vendor/*` ไม่มีหน้า settings ต้องให้ `tenant_admin` แก้ให้เท่านั้น: theme แก้ที่ `/admin/settings` (เป็นระดับ tenant ทั้งร้าน ไม่ใช่ระดับ vendor), เลขบัญชี/ชื่อบัญชี/ธนาคารแก้ที่ `/admin/vendors/[id]/edit`
- **vendor ไม่ได้รับแจ้งเตือนออร์เดอร์ใหม่อัตโนมัติเลย** — `NotifyConfig` เป็น 1 แถวต่อ 1 tenant เท่านั้น (ไม่มี relation ไปยัง `Vendor`) `notifyNewOrder()` (`src/lib/notifications/notifyOrder.ts`) ส่ง Telegram/Email ไปหาแอดมินร้านฝ่ายเดียวตามที่ตั้งไว้ที่ `/admin/notifications` — vendor ต้องเข้ามาเช็คเองที่ `/vendor/orders` (หน้า read-only ไม่มี badge "ใหม่"/unread indicator หรือ real-time update ใดๆ) ถ้าต้องแจ้งเตือน vendor จริงต้องเพิ่ม channel แจ้งเตือนแยกต่อ vendor เอง
