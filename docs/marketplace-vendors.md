# ระบบผู้ขายหลายราย (Marketplace ภายในร้านเดียว)

> กลับไปหน้าหลัก: [../CLAUDE.md](../CLAUDE.md) · โครงสร้างตารางที่เกี่ยวข้อง: `Vendors`, `Products.VendorId`, `Users.VendorId`, `OrderItems.VendorId` ดูที่ [database.md](./database.md)

Roadmap ข้อ 8 — เลือก implement เป็น **"หลายผู้ขายในร้านเดียว"** (คล้าย Shopee/Lazada ที่มีร้านค้าย่อยหลายร้านในแพลตฟอร์มเดียว) ไม่ใช่การขยายระบบ multi-tenant เดิม (แต่ละ tenant ยังคือร้าน/โดเมนแยกกันเหมือนเดิมตาม [theming.md](./theming.md)) — vendor คือผู้ขายรายย่อยที่อยู่**ภายใน** tenant เดียว มีสิทธิ์จัดการเฉพาะสินค้า/ดูออร์เดอร์ของตัวเอง

## บทบาทที่เพิ่มเข้ามา

- **Vendor (ผู้ขาย)** — role ใหม่ใน `Users.Role` (`super_admin | tenant_admin | member | vendor`) ผูกกับ `Users.VendorId` → `Vendors` หนึ่งแถว จัดการได้เฉพาะสินค้าของ vendor ตัวเอง (`Products.VendorId`) และดูออร์เดอร์ที่มีสินค้าของตัวเองอยู่เท่านั้น (อ่านอย่างเดียว ไม่แก้สถานะออร์เดอร์)
- `Products.VendorId` เป็น `NULL ได้` — `NULL` = สินค้าของร้านเอง (house product, จัดการผ่าน seed เหมือนเดิมตามที่ CLAUDE.md บันทึกไว้ว่ายังไม่มีหน้า admin จัดการสินค้าของร้านเอง), ไม่ใช่ `NULL` = สินค้าของ vendor รายนั้น
- `Vendors.Status` = `active | suspended` — แอดมิน tenant กดระงับ vendor ได้จาก `/admin/vendors` โดยไม่ต้องลบข้อมูล สินค้าของ vendor ที่ถูกระงับจะถูกซ่อนจากหน้าร้านทันที (ดูหัวข้อ "การมองเห็นสินค้า" ด้านล่าง) แต่ข้อมูลออร์เดอร์เก่ายังอยู่ครบ

## การจัดการผู้ขาย (แอดมิน)

- `/admin/vendors` (เฉพาะ role `tenant_admin`): เพิ่มผู้ขายใหม่ (กรอกชื่อร้าน, ผู้ติดต่อ, เบอร์โทร, อีเมล+รหัสผ่านเริ่มต้นสำหรับให้ vendor ล็อกอิน, ข้อมูลบัญชีธนาคารไว้อ้างอิงตอนโอนเงินให้ vendor), แก้ไขข้อมูลร้าน/บัญชี, ปุ่มระงับ/เปิดใช้งาน
- สร้าง vendor ใหม่ = สร้าง `Vendor` row + `User` row (role `vendor`) พร้อมกันในทรานแซกชันเดียว — แอดมินเป็นคนตั้งรหัสผ่านเริ่มต้นให้ vendor เอง (ไม่มี flow สมัครสมาชิกสาธารณะสำหรับ vendor ในเฟสนี้ เพื่อกันสแปม/ผู้ขายปลอมเข้าระบบเอง) แล้วแจ้งรหัสผ่านให้ vendor นอกระบบ (เช่น โทร/แชท) — vendor เปลี่ยนรหัสผ่านเองยังไม่มี ทำเพิ่มได้ภายหลังถ้าต้องการ
- ไม่มีปุ่มลบ vendor ถาวร (กันข้อมูลออร์เดอร์เก่าอ้างอิงไม่ได้) ใช้ระงับแทน

## การจัดการสินค้า (ผู้ขาย)

- `/vendor` แดชบอร์ดผู้ขาย (ต้องล็อกอินด้วย role `vendor` — คุมเส้นทางผ่าน `src/proxy.ts` matcher `/vendor/:path*`), แสดงจำนวนสินค้า/รายการที่ถูกสั่งซื้อ และแบนเนอร์เตือนถ้าบัญชีถูกแอดมินระงับ
- `/vendor/products` CRUD สินค้าของตัวเอง (`src/lib/vendor-products/actions.ts`) — ทุก action เช็ค `vendorId` จาก session เทียบกับ `Products.VendorId` เสมอ กัน vendor แก้/ดูสินค้าของ vendor รายอื่น
- ฟอร์มรองรับฟิลด์เดียวกับสินค้าปกติ (ชื่อ, SKU, รายละเอียด, ราคา, ต้นทุน, สต็อก, จังหวัด/หลวงพ่อ/หมวดหมู่, วัด/ยุคสร้าง, ใบรับประกัน) — ใช้คำว่า "พระเครื่อง" แทน "สินค้า" ทั้งฟอร์ม (แก้ตามที่ผู้ใช้ระบุ 2026-08-17), เรียง SKU ไว้ก่อนชื่อ, field บังคับกรอก (SKU/ชื่อ/ราคาขาย/สต็อก) มีดอกจันทร์สีแดงกำกับ, SKU จำกัดไม่เกิน 10 ตัวอักษร (`sku.length > 10` → error "รหัสพระเครื่อง (SKU) ต้องไม่เกิน 10 ตัวอักษร")
- **รูปพระเครื่องรองรับอัปโหลดไฟล์โดยตรงและหลายรูปแล้ว** (เปลี่ยนจาก URL เดิม/รูปเดียวตามที่ผู้ใช้ระบุ 2026-08-17) — จำกัด JPG/PNG/WebP ไม่เกิน 5MB ต่อไฟล์ (`uploadProductImageFile()`, `src/lib/vendor-products/uploadImage.ts`) เก็บไว้ที่ `public/uploads/products/` บนดิสก์เครื่อง dev เอง — เป็นทางลัดสำหรับ dev ตาม pattern เดียวกับสลิปโอนเงิน (`src/lib/checkout/uploadSlip.ts`) ตาม CLAUDE.md ("ตอน dev ใช้ placeholder ก่อน") **โปรดักชันจริงต้องเปลี่ยนไปใช้ object storage (S3)** เหมือนกัน
  - **รูปพระเครื่องหลัก (`ProductImage.imageType = "product"`)**: บังคับอัปโหลดตอนสร้างใหม่อย่างน้อย 1 รูป ไม่เกิน 10 รูป — ตอนแก้ไข ถ้าอัปโหลดไฟล์ใหม่จะ**แทนที่ชุดรูปเดิมทั้งหมด** (validate 1-10 เฉพาะตอนมีไฟล์ใหม่) ถ้าปล่อยว่างไว้จะคงรูปเดิมไว้ไม่แตะต้อง
  - **รูปใบรับประกัน (`ProductImage.imageType = "certificate"`)**: โชว์ช่องอัปโหลดแยกก็ต่อเมื่อติ๊ก "มีใบรับประกัน" (React state `hasCertificate` toggle การแสดงผลใน `ProductForm.tsx`) — บังคับอย่างน้อย 1 รูป ไม่เกิน 3 รูป ถ้าเลือกมีใบรับประกัน ตอนแก้ไขถ้าไม่ติ๊กแล้ว ระบบจะลบรูปใบรับประกันเดิมทั้งหมดออกด้วย (คู่กับการเคลียร์ `certificateInfo` เป็น `null` ที่มีอยู่แล้ว)
  - ฟอร์มแก้ไขโชว์รูปปัจจุบันทั้งหมดเป็น preview grid ทั้งสองประเภท
- ปิดการขาย (`isActive = false`) แทนการลบ — สินค้าที่เคยอยู่ในออร์เดอร์เก่ายังอ้างอิงได้ปกติ (เหมือน pattern เดิมของระบบ)

## การมองเห็นสินค้าบนหน้าร้าน

- ทุก query สินค้าฝั่ง storefront (`src/lib/products/queries.ts`, `home/queries.ts`, `provinces/queries.ts`, `monks/queries.ts`) ใช้ตัวกรองร่วม `visibleVendorFilter` (export จาก `products/queries.ts`): แสดงเฉพาะสินค้าที่ `VendorId IS NULL` (สินค้าของร้านเอง) **หรือ** vendor ของสินค้านั้นยังไม่ถูกระงับ (`Vendor.Status != "suspended"`)
- **สำคัญ:** เพิ่ม query สินค้าฝั่ง storefront ใหม่ทุกครั้งต้อง spread `visibleVendorFilter` เข้า `where` ด้วยเสมอ ไม่งั้นสินค้าของ vendor ที่ถูกระงับจะยังโผล่อยู่
- `ProductCard` และหน้ารายละเอียดสินค้าโชว์ป้าย "ขายโดย {ชื่อร้าน}" เมื่อสินค้ามี vendor (ไม่โชว์ถ้าเป็นสินค้าของร้านเอง)
- **ลูกค้าเห็นสินค้าของทุก vendor ที่ active ปนกันในหน้าร้านเดียวกันหมด** (`/`, `/products`, `/provinces/[slug]`, `/monks/[slug]`) — `visibleVendorFilter` ไม่ได้แยกว่าลูกค้าคนไหนควรเห็นของ vendor ไหน แค่กรอง vendor ที่ถูกระงับออกเท่านั้น ตัวกรองที่มีตอนนี้คือจังหวัด/หลวงพ่อ/หมวดหมู่/ช่วงราคา **ไม่มีตัวกรองเลือกดูเฉพาะ vendor ใดวันหนึ่ง** และ**ไม่มีหน้าร้านย่อยสาธารณะของแต่ละ vendor** (เช่น `/shop/[vendorSlug]`) ให้ลูกค้ากดเข้าไปดูเฉพาะสินค้าของ vendor รายนั้น — ป้าย "ขายโดย" ด้านบนเป็นแค่ข้อมูลบอก ไม่ใช่ลิงก์ไปหน้าอื่น

## Checkout และออร์เดอร์

- **ไม่มีการแยกออร์เดอร์/การจ่ายเงินตาม vendor** — ตะกร้าที่มีสินค้าจากหลาย vendor ปนกับสินค้าของร้านเองยังสร้างเป็น `Order` เดียวเหมือนเดิมทุกประการ ลูกค้าจ่ายเงินเป็นก้อนเดียว ไม่ใช่ split-payment แบบ marketplace เต็มรูป (จุดนี้ไม่เปลี่ยน)
- **การจัดส่งแยกตาม vendor ได้ (แก้ไข 2026-08-14, กลับคำตัดสินใจเดิม)** — เดิมเอกสารนี้เคยระบุว่า "จัดส่งเป็นก้อนเดียว ไม่รองรับ vendor แยกกล่องส่งเอง" แต่พิจารณาใหม่แล้วว่าไม่ตรงกับความเป็นจริง เพราะ vendor แต่ละรายเก็บสต็อกและแพ็คของเอง (ไม่ได้ส่งสต็อกมารวมที่คลังร้านล่วงหน้าแบบ Amazon FBA) การบังคับให้พัสดุออกจากที่เดียวจะต้องเพิ่ม flow ใหม่ทั้งหมด (vendor ส่งของมาที่ร้านก่อน แล้วร้านค่อยแพ็ครวมส่งลูกค้าอีกที) ซึ่งเพิ่มขั้นตอน/ต้นทุนขนส่งโดยไม่จำเป็นและไม่เคยอยู่ในแผนเดิม — เปลี่ยนเป็นให้แต่ละ vendor (และร้านเอง ถ้ามีสินค้าของร้านปนอยู่ด้วย) ส่งพัสดุแยกกันตรงถึงลูกค้า **1 order อาจมีหลาย tracking number** (หนึ่งต่อ vendor ที่มีสินค้าในออร์เดอร์นั้น) — ตรงกับพฤติกรรมจริงของ marketplace รายใหญ่ (Shopee/Lazada ก็แยกพัสดุ/tracking ต่อผู้ขายเหมือนกันเมื่อ order มีสินค้าหลายร้าน) ลูกค้าเห็นทุก tracking number ของ order นั้นพร้อมกันที่ `/track-order` — schema/flow เต็ม (ตาราง `Shipment`, ลิงก์ 17TRACK) ทำเสร็จแล้ว ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านล่าง และ [checkout-and-payment.md](./checkout-and-payment.md) หัวข้อ "หน้าติดตามสถานะออร์เดอร์"
- `OrderItems.VendorId` snapshot ผู้ขาย ณ เวลาซื้อไว้ (เหมือน `ProductName` ที่ snapshot ชื่อสินค้า) กันกรณีสินค้าย้ายเจ้าของ/vendor ถูกลบทีหลัง ทำให้ประวัติออร์เดอร์เก่ายังถูกต้อง — `createOrderAction` (`src/lib/checkout/actions.ts`) อ่าน `product.vendorId` มาใส่ตอนสร้าง `OrderItem` ทุกครั้ง
- `/vendor/orders` อ่านอย่างเดียว: group `OrderItem` ตาม `orderId` แล้วโชว์เฉพาะรายการสินค้าของ vendor ตัวเองในแต่ละออร์เดอร์ + ยอดรวมเฉพาะส่วนของตัวเอง — vendor **ไม่เห็น**รายการสินค้าของ vendor อื่นหรือของร้านเองในออร์เดอร์เดียวกัน และ**แก้สถานะออร์เดอร์ไม่ได้** (สถานะ/การจัดส่งยังเป็นหน้าที่ tenant_admin ที่ `/admin/orders/[id]` เหมือนเดิม)

## ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว

- **รหัสสินค้า (SKU/product code)** (เสร็จแล้ว 2026-08-16, แก้ไขเพิ่มเติม 2026-08-17) — vendor กรอกเองตอนเพิ่ม/แก้ไขสินค้าที่ `/vendor/products/new` และ `/vendor/products/[id]/edit` (บังคับกรอกเสมอสำหรับสินค้าที่สร้าง/แก้ไขใหม่ — สินค้าเก่าที่ seed ไว้ยังเป็น `NULL` ได้ และ**จำกัดไม่เกิน 10 ตัวอักษร** ตามที่ผู้ใช้ระบุ 2026-08-17) ไม่ซ้ำกันภายในร้านเดียวกัน (unique filtered index `UX_Products_Tenant_Sku` ต่อ `TenantId`, ข้ามร้านซ้ำกันได้) เช็คซ้ำทั้งฝั่ง client (`required`, `maxLength`) และ server (`src/lib/vendor-products/actions.ts` คืน error "รหัสพระเครื่องนี้มีอยู่แล้วในร้าน" ถ้าซ้ำ) — **ไม่ได้ snapshot ลง `OrderItem`** ต่างจาก `ProductName`/`VendorId` เพราะ SKU ถือเป็น identifier ที่เสถียร ไม่ต้องเก็บ historical snapshot จึง join สดจาก `Product.Sku` ตอน query แทน
  - แสดงผลในหน้าฝั่งแอดมิน/vendor เท่านั้น: รายการสินค้าของ vendor (`/vendor/products`), รายละเอียดออร์เดอร์ทั้งฝั่งแอดมิน (`/admin/orders/[id]`) และฝั่ง vendor (`/vendor/orders`) — **ถอดออกจากหน้ารายละเอียดสินค้า (`/products/[id]`) และตะกร้า (`/cart`) แล้ว (2026-08-17)** ตามที่ผู้ใช้ระบุว่าไม่ต้องการให้ลูกค้าเห็นรหัส SKU ตอนสั่งซื้อ (กันลูกค้าสับสนถ้าเห็นรหัสที่ดูคล้ายกัน) — ต่างจาก requirement เดิมตอนสร้างฟีเจอร์นี้ (2026-08-16) ที่เคยให้โชว์ครบทุกจุดรวมฝั่งลูกค้าด้วย
  - ทดสอบ end-to-end จริงแล้วใน browser: vendor เพิ่มสินค้าพร้อม SKU สำเร็จ, กันรหัสซ้ำในร้านเดียวกันได้ถูกต้อง, ออร์เดอร์เก่าที่ไม่มี SKU (`NULL`) ยัง render ได้ปกติไม่พัง, และยืนยันแล้วว่าหน้ารายละเอียดสินค้า/ตะกร้าไม่แสดง SKU อีกต่อไป (2026-08-17)
- **vendor เปลี่ยนรหัสผ่านเองได้** (เสร็จแล้ว 2026-08-16) — หน้าใหม่ `/vendor/settings` (ลิงก์จาก `/vendor` dashboard) มีฟอร์มกรอกรหัสผ่านเดิม + รหัสผ่านใหม่ + ยืนยันรหัสผ่านใหม่ — action `changeVendorPasswordAction` (`src/lib/auth/actions.ts`) เช็ครหัสผ่านเดิมถูกต้องด้วย `verifyPassword()` ก่อนเสมอ (คืน error "รหัสผ่านเดิมไม่ถูกต้อง" ถ้าไม่ตรง), บังคับรหัสผ่านใหม่อย่างน้อย 8 ตัวอักษรและต้องตรงกับช่องยืนยัน (pattern เดียวกับตอนสมัครสมาชิก) แล้ว hash ด้วย `hashPassword()` ก่อนอัปเดต `Users.PasswordHash` — สำเร็จแล้ว redirect กลับหน้าเดิมพร้อม `?success=1` แสดงข้อความ "เปลี่ยนรหัสผ่านสำเร็จ" — ทดสอบ end-to-end จริงแล้วใน browser (2026-08-16): กรอกรหัสผ่านเดิมผิด → error ถูกต้อง, กรอกรหัสผ่านใหม่ไม่ตรงกับยืนยัน → error ถูกต้อง, เปลี่ยนรหัสผ่านสำเร็จ → logout → login ด้วยรหัสผ่านใหม่ได้จริง ("ลืมรหัสผ่าน" ตอนยังไม่ได้ login ไม่รวมอยู่ในฟีเจอร์นี้ ยังเป็นข้อจำกัดเดิมเหมือน member)
- **แจ้งเตือน vendor เมื่อมีออร์เดอร์ใหม่** (เสร็จแล้ว 2026-08-16) — ดูรายละเอียด flow เต็มที่ [checkout-and-payment.md](./checkout-and-payment.md) หัวข้อ "หลังส่งฟอร์มสำเร็จ — ระบบแจ้งเตือน" — สรุปสั้นๆ: เพิ่ม `Vendors.TelegramChatId`/`NotifyTelegramEnabled`/`NotifyEmailEnabled`, กรอกให้ที่ `/admin/vendors/[id]/edit` (ไม่ต้องรอ vendor self-service settings), ใช้ bot token ร่วมจาก `NotifyConfig` ของ tenant เดิมแต่ส่งไปที่ chat id ของ vendor แต่ละราย, อีเมลใช้ `Users.Email` เดิมของ user ที่ผูก vendor นั้น (ยัง stub อยู่เหมือนฝั่งแอดมิน) — `notifyVendorNewOrder()` (`src/lib/notifications/notifyOrder.ts`) เรียกแยกต่างหากจาก `notifyNewOrder()` เดิมที่แจ้งแอดมิน (ไม่ได้แก้ของเดิม) วนเรียกต่อทุก `vendorId` ที่แตกต่างกันในออร์เดอร์นั้น (ตอนสร้างออร์เดอร์ใหม่จริง) — ทดสอบจริงแล้วใน browser (2026-08-16): admin ตั้งค่า chat id + เปิดใช้งานทั้งสองช่องทางให้ vendor สำเร็จ → ลูกค้าสั่งซื้อสินค้าของ vendor รายนั้น → เห็น log แจ้งเตือน vendor แยกจาก log แจ้งเตือนแอดมินชัดเจน ไม่กระทบการสร้างออร์เดอร์แม้แจ้งเตือนจะล้มเหลว (bot token ที่ตั้งไว้ตอน dev เป็น token ปลอม)
- **หน้าแอดมินสรุป/ส่งรายการสั่งซื้อให้ vendor พร้อมปุ่ม "Send Notify"** (เสร็จแล้ว 2026-08-17) — เพิ่มใน `/admin/orders/[id]` เดิม (ไม่ได้ทำหน้าแยกใหม่ ตามที่ตกลงไว้ว่า scope คือ "ต่อ order" ไม่ใช่ "รวมทุก order ของ vendor"): ส่วน "แยกตามผู้ขาย" แสดงเฉพาะเมื่อ order นั้นมีสินค้าของ vendor อย่างน้อย 1 ราย — group `OrderItem` ตาม `vendorId` (`null` = "สินค้าของร้านเอง" ไม่มีปุ่ม), แต่ละแถวโชว์ "ที่อยู่ลูกค้า {fullName} — {ชื่อร้าน vendor} มี N รายการ" พร้อมปุ่ม **Send Notify ต่อแถว** (action ใหม่ `sendVendorNotifyAction` ใน `src/lib/admin-orders/actions.ts` เรียก `notifyVendorNewOrder()` เดิมจากข้อ 3 ตรงๆ ระบุ `orderNumber` ให้ vendor รู้ว่า order ไหน — ไม่ใช่ fire-and-forget เหมือนตอนสร้างออร์เดอร์ เพราะปุ่มนี้ผู้ใช้กดเองไม่ใช่ path ที่ต้อง block/ไม่ block ลูกค้า) กดแล้ว redirect กลับมาหน้าเดิมพร้อม query `?notified={vendorId}` โชว์ข้อความยืนยัน "ส่งแจ้งเตือนไปยัง {ชื่อร้าน} แล้ว" — ไม่มี state เก็บว่า "notify แล้วหรือยัง" ใน DB (กดซ้ำได้เรื่อยๆ ไม่จำกัด เป็นแค่ trigger ส่งซ้ำ manual)
  - `/vendor/orders` เดิม (group `OrderItem` ตาม `orderId`, กรองเฉพาะของ vendor ตัวเองอยู่แล้วจาก `where: { vendorId: session.vendorId }`) เพิ่มแค่บรรทัดที่อยู่จัดส่งของแต่ละ order ที่ยังไม่มี — ไม่ต้องเพิ่ม gating ตามสถานะ notify เพราะ query เดิมกรอง `vendorId` ให้แล้วเป็นการแยกข้อมูลต่อ vendor อยู่แล้วโดยธรรมชาติ (vendor ไม่เคยเห็นยอดรวม/ของ vendor อื่นในหน้านี้อยู่แล้วไม่ว่าจะกด Send Notify หรือไม่)
  - ทดสอบจริงแล้วใน browser (2026-08-17) โดยใช้ order เดิมที่มี 2 vendor ปนกัน (order ทดสอบ marketplace 2 รายการจาก item 8): เห็น breakdown ถูกต้อง ("ร้านพระเครื่องสมชาย มี 1 รายการ" / "สินค้าของร้านเอง มี 1 รายการ") → กด Send Notify ของ vendor รายเดียวที่มี → เห็นข้อความยืนยันถูกต้อง + server log ยิง `notifyVendorNewOrder` เฉพาะ vendor นั้นจริง (ไม่กระทบ log ฝั่งแอดมิน) → login เป็น vendor เข้า `/vendor/orders` เห็นที่อยู่จัดส่งครบถูกต้อง และเห็นเฉพาะยอด/รายการของตัวเอง (990 บาท) ไม่เห็นยอดรวม order (5,261 บาท) หรือรายการของสินค้าร้านเองเลย
- **เลขพัสดุ/tracking number ต่อ vendor** (เสร็จแล้ว 2026-08-17) — ดูรายละเอียด schema/flow เต็มที่ [checkout-and-payment.md](./checkout-and-payment.md) หัวข้อ "หน้าติดตามสถานะออร์เดอร์" — สรุปสั้นๆ: ตารางใหม่ `Shipment` (`orderId`, `vendorId` nullable, `carrierName`, `trackingNumber`, `shippedAt`) รองรับ **1 order หลาย shipment** ตามที่ตัดสินใจไว้ในหัวข้อ "Checkout และออร์เดอร์" ด้านบน — vendor กรอกเลขพัสดุของตัวเองเองได้ที่ `/vendor/orders` (`saveVendorShipmentAction`), tenant_admin กรอกแทนได้เฉพาะสินค้าของร้านเองที่ `/admin/orders/[id]` (`saveHouseShipmentAction`) — ลิงก์ติดตามใช้ 17TRACK อย่างเดียวทุกขนส่ง (`buildTrackingUrl()`) ไม่ auto-generate URL แยกต่อขนส่งเอง (`carrierName` เก็บไว้แสดงผลอย่างเดียว) — แสดงลิงก์กดได้ที่ `/track-order` (ลูกค้า), `/admin/orders/[id]` (ส่วน "การจัดส่ง (เลขพัสดุ)" breakdown ต่อ vendor/ร้านเองคู่กับส่วน "แยกตามผู้ขาย"), `/vendor/orders` — ไม่ต่อ API ขนส่งดึงสถานะเรียลไทม์ และไม่มีแจ้งเตือนลูกค้าอัตโนมัติทันทีที่กรอกเลขพัสดุจริง (มี hook เตรียมไว้เฉยๆ ที่ `notifyCustomerShipped()` แต่ยังไม่มีจุดเรียกใช้งาน) — ทดสอบจริงแล้วใน browser (2026-08-17): vendor กรอกเลขพัสดุสำเร็จ, ลิงก์ 17TRACK generate ถูกต้องตามฟอร์แมตและเปิดหน้าจริงได้ (เลขพัสดุทดสอบไม่ใช่พัสดุจริงจึงหาผลลัพธ์ไม่เจอ เป็นเรื่องคาดหมาย), เห็นตรงกันทั้ง 3 จุด (`/vendor/orders`, `/admin/orders/[id]`, `/track-order`), tenant_admin กรอกเลขพัสดุของสินค้าร้านเองในอีก order ไม่กระทบ shipment ของ vendor
- **ระบบ payout/commission** (เสร็จแล้ว 2026-08-17 — ข้อสุดท้ายของ roadmap ข้อ 9, ครบทั้ง 6 ข้อแล้ว) — เพิ่ม `Tenants.EscrowDays` (default 7 วัน)/`Tenants.PayoutCycleDays` (default 15 วัน, แก้ได้ที่ `/admin/settings`), `Vendors.CommissionPercent` (default 10%, แก้ได้ที่ `/admin/vendors/[id]/edit`), `OrderItems.PayoutStatus` (`pending | eligible | paid`) + `PayoutEligibleAt` + `PayoutBatchId`, ตารางใหม่ `VendorPayoutBatch`
  - **ไม่มี cron job จริง** (ตาม pattern เดิมของโปรเจกต์ที่ใช้ manual trigger แทน background job เสมอ เช่น ตรวจสลิป/แจ้งเตือน) — แบ่งเป็น 2 จุดที่ทำงานคนละเวลา: (1) `updateOrderStatusAction` (`src/lib/admin-orders/actions.ts`) คำนวณ `payoutEligibleAt = shippedAt + tenant.escrowDays` ให้ `OrderItem` ที่มี `vendorId` ทุกครั้งที่ order เปลี่ยนเป็น `shipped` ครั้งแรก (2) tenant_admin กดปุ่ม **"สร้างรอบจ่ายใหม่"** เองที่ `/admin/vendors/[id]/payouts` (`createPayoutBatchAction`, `src/lib/payouts/actions.ts`) — ดึงเฉพาะ `OrderItem` ที่ `payoutStatus = pending`, `payoutEligibleAt` ผ่านมาแล้ว, ยังไม่เคย batch (`payoutBatchId IS NULL`) มารวมเป็น `VendorPayoutBatch` ก้อนเดียว (คำนวณ `commissionAmount` จาก `vendor.commissionPercent` ณ ตอนนั้น — ไม่ recalculate ย้อนหลังถ้า commission % เปลี่ยนทีหลัง, `gatewayFeeAmount` เป็น 0 เสมอตามที่ตัดขอบเขตไว้) แล้วตั้ง `payoutStatus = eligible` ให้รายการที่ถูก batch — `periodStart` ของรอบใหม่ = `periodEnd` ของรอบก่อนหน้า (หรือ `vendor.createdAt` ถ้ายังไม่เคยมีรอบ), `periodEnd` = เวลาที่กดสร้างรอบ
  - ปุ่ม **"ทำเครื่องหมายว่าจ่ายแล้ว"** (`markPayoutBatchPaidAction`) ต่อรอบ — อัปเดต `VendorPayoutBatch.status = paid` + `paidAt` พร้อมกับ `OrderItems.payoutStatus = paid` ทุกรายการในรอบนั้นในทรานแซกชันเดียว ไม่มีการโอนเงินอัตโนมัติจริงตามที่ตัดขอบเขตไว้แต่แรก
  - หน้า `/admin/vendors/[id]/payouts` (ลิงก์จาก `/admin/vendors` และหน้าแก้ไขผู้ขาย) แสดง 2 ยอดแยกกันชัดเจนก่อนกดสร้างรอบ: "ยอดที่ยังไม่พ้นระยะ escrow" กับ "ยอดที่พร้อมจัดเข้ารอบจ่าย" (ปุ่มสร้างรอบ disable ถ้ายอดหลังเป็น 0) + ประวัติรอบจ่ายทั้งหมดพร้อม breakdown ยอดขายรวม/ค่าคอมมิชชั่น/ค่าธรรมเนียม gateway/ยอดสุทธิ
  - ทดสอบจริงแล้วใน browser (2026-08-17): ยืนยัน `Tenant.escrowDays`/`payoutCycleDays` default 7/15 และ `Vendor.commissionPercent` default 10% ถูกต้องตั้งแต่แรกสร้าง — ตั้ง `escrowDays = 0` ชั่วคราวแล้ว ship คนละ order สองใบ (ใบแรก ship ตอน escrow ยังเป็น 7 วัน → ค้างอยู่ฝั่ง "ยังไม่พ้นระยะ escrow" ถูกต้อง, ใบที่สอง ship ตอน escrow = 0 → ขึ้นฝั่ง "พร้อมจัดเข้ารอบจ่าย" ถูกต้อง) → กดสร้างรอบจ่าย เห็นเฉพาะรายการที่พ้น escrow ถูกดึงเข้ารอบ (อีกใบไม่ถูกจัดเข้ารอบ ตรงตาม requirement) → เลขคำนวณถูกต้อง (990 บาท, commission 10% = 99 บาท, สุทธิ 891 บาท) → แก้ commission % ของ vendor เป็น 15% แล้วเช็คว่ารอบเก่าที่จ่ายไปแล้วยังโชว์เลข 10% เดิม (snapshot ไม่ recalculate ย้อนหลัง) → กด "ทำเครื่องหมายว่าจ่ายแล้ว" สถานะเปลี่ยนเป็น "จ่ายแล้ว" พร้อมเวลาที่จ่ายถูกต้อง

## แผนที่จะเพิ่ม

ครบทั้ง 6 ข้อของ roadmap ข้อ 9 แล้ว (ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน) — ไม่มีรายการค้างในหัวข้อนี้อีก

## ขอบเขตที่ยังไม่ทำ (ตัดสินใจจำกัด scope ตอนสร้างฟีเจอร์นี้)

- **ไม่มี logic คำนวณค่าธรรมเนียม gateway จริง** — `VendorPayoutBatch.GatewayFeeAmount` เตรียม field ไว้แล้วแต่ค่าเป็น 0 เสมอในตอนนี้ เพราะ payment gateway ปัจจุบันเป็น mock ไม่มีผู้ให้บริการจริงที่มี fee schedule ให้อ้างอิง (ดู [checkout-and-payment.md](./checkout-and-payment.md) หัวข้อ "Payment gateway (จำลอง)") — รอต่อ gateway จริงในอนาคตแล้วค่อยกรอกค่าเข้ามาใช้งาน
- **ไม่มีการโอนเงินอัตโนมัติจริง/ไม่มี instant payout** — ไม่ต่อ bank API/PromptPay transfer API จริง ระบบแค่คำนวณ/สรุปยอดที่ต้องจ่ายให้ถูกต้องต่อรอบ ส่วนการโอนจริงแอดมินยังกดโอนเองนอกระบบเหมือนเดิม แล้วมาติ๊กว่า "จ่ายแล้ว" ในระบบ (ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน)
- **ไม่มี cron/background job สร้างรอบจ่ายอัตโนมัติตามรอบ** — `Tenant.PayoutCycleDays` เป็นแค่ข้อมูลอ้างอิงที่แสดงในหน้าตั้งค่า ไม่มี logic บังคับให้สร้างรอบใหม่ทุก N วันจริง ตอนนี้ tenant_admin เป็นคนกดปุ่ม "สร้างรอบจ่ายใหม่" เอง (ตรงกับ pattern manual-trigger เดิมของทั้งโปรเจกต์)
- **ไม่มี public vendor registration/approval flow** — เฉพาะ tenant_admin สร้างบัญชี vendor ให้เท่านั้น
- ~~ไม่มี split-shipping ต่อ vendor~~ **ยกเลิกข้อจำกัดนี้แล้ว (2026-08-14) และทำเลขพัสดุ/tracking number เสร็จแล้ว (2026-08-17)** — รองรับ split-shipping ต่อ vendor (1 order อาจมีหลาย tracking number) ดูหัวข้อ "Checkout และออร์เดอร์" และ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน
- ~~vendor เปลี่ยนรหัสผ่านเองยังไม่มี~~ **ทำแล้ว (2026-08-16)** — ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน ("ลืมรหัสผ่าน" ตอนยังไม่ได้ login ยังไม่รวมอยู่ในนี้ ยังเป็นข้อจำกัดเดิม เหมือนกับ member ที่ยังไม่มีหน้า "ลืมรหัสผ่าน" เช่นกัน)
- **vendor แก้ theme ร้านหรือเลขบัญชีธนาคารรับเงินของตัวเองไม่ได้** — พอร์ทัล `/vendor/*` ไม่มีหน้า settings ต้องให้ `tenant_admin` แก้ให้เท่านั้น: theme แก้ที่ `/admin/settings` (เป็นระดับ tenant ทั้งร้าน ไม่ใช่ระดับ vendor), เลขบัญชี/ชื่อบัญชี/ธนาคารแก้ที่ `/admin/vendors/[id]/edit`
- ~~vendor ไม่ได้รับแจ้งเตือนออร์เดอร์ใหม่อัตโนมัติเลย~~ **ทำแล้ว (2026-08-16)** — ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน
- ~~ไม่มีปุ่ม "Send Notify" ให้แอดมินสั่งแจ้งเตือนซ้ำเองแบบ manual ต่อ order/ต่อ vendor~~ **ทำแล้ว (2026-08-17)** — ดูหัวข้อ "ฟีเจอร์เสริมฝั่ง vendor ที่ทำแล้ว" ด้านบน — ยังไม่มี badge "ใหม่"/unread indicator หรือ real-time update ที่ `/vendor/orders` (vendor ต้องเข้ามาดูเองอยู่ดีหลังได้รับแจ้งเตือน)
